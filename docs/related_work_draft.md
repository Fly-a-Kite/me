# Related Work Draft

## 相关工作

现有与本项目相关的研究大致可以分为三条主线。第一条是面向 DataFrame 或数据分析工作流的 workload generation 与 replay，这类工作关注如何构造更像真实分析任务的数据处理程序，并将其重放到不同系统上进行压力测试、性能评估或回归检查。第二条是面向 SQL/DBMS 的 logic-bug testing，这类工作围绕错误结果而非 crash 设计测试 oracle，通过等价变换、参考执行、结果分区或跨语句一致性来检测成熟数据库系统中的 silent wrong-result bugs。第三条是 guided testing 与 metamorphic testing，这类工作试图用 coverage、query plan、language validity 或变形关系等信号，提高测试生成效率、覆盖更深层执行路径，或在缺少外部 ground truth 的情况下构造可自动判定的正确性条件。

本项目与上述三条线都有直接联系，但又不与其中任何一条完全重合。与 DataFrame workload generation 工作相比，本项目不只是为了生成可 replay 的 workflow，也不只是为了做 stress testing 或 benchmark，而是要用统一的语义层直接发现并归档 latest-version 的真实实现错误。与 SQL/DBMS logic-bug testing 工作相比，本项目不局限于 SQL 这一种输入接口，也不局限于单一 DBMS，而是同时覆盖 Python DataFrame API、Arrow table compute、embedded SQL engine 和 query engine。与 guided testing 和 metamorphic testing 工作相比，本项目并不是把 guidance 或 metamorphic relation 作为单一创新点，而是将它们作为统一 discovery-runing pipeline 中的组成部分，与 semantic normalization、deterministic probe、candidate reduction、issue bundling 和 confirmation tracking 串成同一条证据链。

更具体地说，本项目最接近但又明显不同于两类工作。第一类是以 FuzzyData 为代表的 DataFrame workflow generation 工作。第二类是以 SQLancer 及其衍生 oracle、SQLRight、QPG 和 DQE 为代表的 DBMS wrong-result bug 检测工作。前者与本项目共享“抽象 workflow 表示”和“跨后端 replay”这两个基本思想，但它们的主要目标是 workload generation、性能比较和 stress testing，而不是以 latest-version confirmed bug family 为中心组织实验与证据。后者与本项目共享“wrong-result bug 比 crash 更难检测但更值得研究”“需要自动 oracle”“需要 grammar/semantic-aware generation 或 guidance”这些出发点，但它们的测试对象通常仍是单一 SQL DBMS 或单一 query engine，很少处理 Python API、Arrow layout、eager/lazy execution、API lowering 和跨 family 语义归一化等问题。

从论文叙事上看，本项目最不应该宣称自己“首次测试 DataFrame 系统”或“首次做数据系统 fuzzing”。这些说法很容易被 FuzzyData、BigFuzz、SparkFuzz 以及 SQLancer 一系工作反驳。更稳妥也更准确的定位是：本项目提出了一套面向 DataFrame/Arrow/embedded analytical engines 的统一语义差分测试框架，在同一套 DSL、normalizer、oracle、triage 和 evidence pipeline 下，同时支持跨后端差分测试、metamorphic checking、deterministic latest-version audit，以及 latest-version candidate 到 confirmed bug family 的完整证据管理流程。换句话说，本项目的创新不在于“第一次生成随机查询”或“第一次做变形测试”，而在于把原本分散在 DataFrame workflow testing、DBMS logic-bug testing 和 declarative engine metamorphic testing 里的方法元素，整合成一套跨生态、以 bug evidence 为导向的统一测试系统。

### DataFrame 与数据分析工作流测试

在面向 DataFrame 系统的研究中，最接近本项目的是 FuzzyData。FuzzyData 提出了一个抽象的数据处理 workflow 模型，能够生成随机表和随机 workflow，并把这些 workflow replay 到 pandas、modin、SQLite 等 client 上，用于 stress testing、performance evaluation 和 bottleneck analysis。FuzzyData 的重要意义在于，它较早意识到 dataframe-based systems 既不同于传统关系数据库，也不同于简单的 key-value benchmark 场景，因此需要独立的 workload representation 与 generation framework。它和本项目的相似之处主要体现在三个方面。第一，两者都认为单纯使用手写静态 workload 无法充分覆盖现代数据处理系统的行为差异。第二，两者都使用抽象工作流表示，而不是直接把某一种底层 API 调用序列当作唯一输入语言。第三，两者都支持将同类工作流重放到多个后端，以观察行为或性能差异。

但 FuzzyData 与本项目的差异也非常关键。首先，FuzzyData 的核心目标是 workload generation、scalability、replay 和 performance comparison，而不是围绕真实 bug family 的 latest-version 正确性审计。其次，FuzzyData 虽然提到 correctness bug，但 correctness 并不是其主要评价维度，也没有围绕 semantic differential oracle、metamorphic oracle、deterministic probe、candidate family classification、saturated-family filtering 或 upstream confirmation tracking 组织整套系统。再次，FuzzyData 测试的后端集合虽然跨越多个 dataframe clients，但并没有显式地把 Python DataFrame API、Arrow compute、embedded SQL engine 和 query engine 统一为同一语义测试面。因此，如果 reviewer 认为本项目与 FuzzyData 接近，最合理的回应不是否认相似性，而是明确说明：FuzzyData 解决的是“如何生成和重放 DataFrame workload”，而本项目解决的是“如何在异构数据处理后端上用统一语义和统一证据链自动发现、去重、复现并上报 latest-version wrong-result bugs”。

BigFuzz 则代表了另一种 data analytics fuzzing 思路。它的测试目标是大数据分析应用本身，而不是底层 dataframe 或 query engine 的跨后端语义一致性。BigFuzz 使用 framework abstraction 和 schema-aware mutation，试图提高 fuzz testing 在 data-centric analytics applications 上的效率。这和本项目的共同点在于，两者都不满足于字节级随机变异，也都认为只有理解数据模式与程序结构，才能构造更有效的测试用例。然而，BigFuzz 的被测对象是 analytics application 的逻辑，而本项目的被测对象是基础数据处理引擎本身。BigFuzz 不需要统一多个执行模型的结果归一化，也不需要处理 DataFrame API、Arrow layout semantics、embedded SQL 和 query engine 之间的异构语义边界。因此，BigFuzz 更像“面向数据分析应用的结构化 fuzzing”，而本项目更像“面向数据处理生态基础设施的语义一致性 fuzzing”。

SparkFuzz 是 query engine correctness testing 的一个重要邻近工作。它通过随机生成数据和 SQL 查询，并将 Spark SQL 的结果与 PostgreSQL 等参考系统对比，来发现 Spark SQL 的 correctness regressions。SparkFuzz 与本项目有几个实质性相似点：两者都关注 wrong-result bugs 而不仅是崩溃；都依赖随机数据与查询生成；都假设成熟分析引擎会因持续演进和复杂优化链而引入 correctness regressions；都把对比执行结果作为核心测试信号之一。但 SparkFuzz 本质上仍是一个以 SQL engine 为中心的单域系统，其输入语言和参考机制都围绕 SQL 展开。相较之下，本项目需要同时处理非 SQL 风格的 Python DataFrame API、Arrow compute 路径、DuckDB/SQLite/DataFusion 的 SQL 或 query interface，以及 Polars eager/lazy/streaming 这种执行模式差异。这意味着本项目不仅要生成测试程序，还要解决跨执行模型的语义对齐、结果 canonicalization、family-level triage 和 latest-version evidence reporting 等问题。因此，SparkFuzz 可以被视为本项目在“现代分析引擎 correctness fuzzing”这部分最接近的祖先工作之一，但它并没有进入本项目真正困难的跨生态统一语义问题。

### SQL/DBMS 逻辑错误测试

DBMS wrong-result bug testing 是与本项目关系最紧密的一条文献线，因为它提供了大量关于 oracle 设计、等价变换、bug family 计数和 mature systems bug discovery 的经验。这里最重要的一组工作是 PQS、NoREC、TLP 和 DQE。它们共同的特点是，不依赖人工给定 ground truth，而是通过构造理论上应当等价或一致的多个执行结果，自动判断系统是否出现 silent wrong-result。

PQS 的测试目标是 relational DBMS 中 SELECT 查询的逻辑错误。它的测试目的，是通过构造一个理论上必须返回某个 pivot row 的查询，来验证目标 DBMS 是否遗漏该行。PQS 与本项目的共同点在于，都把 oracle 设计放在系统核心位置，也都面向 silent wrong-result bugs 而不是 crash。然而，PQS 的 oracle 以“一个 pivot row 是否应被返回”为中心，需要围绕 SQL 表达式语义构造查询；它的适用对象是 SQL DBMS，而不是 Python DataFrame API、Arrow table compute 或 query engine interface。更重要的是，PQS 的正确性判定仍然发生在单一 DBMS 的 SQL 世界里，而本项目的判定往往需要跨 family 比较多个完全不同后端的 normalized outputs。因此，PQS 对本项目最大的启发是“正确性 oracle 比盲目增加输入复杂度更关键”，而不是在输入表示或系统范围上与本项目相同。

NoREC 的测试目标是 DBMS optimizer 导致的 wrong-result bugs。它的测试目的，是把一个可能被优化的查询改写成一个不容易被优化的 reference form，再比较两者的结果是否一致。NoREC 与本项目的相似性更强，因为它同样依赖语义等价变换，并且 explicitly 关注 mature systems 中的 silent logic bugs。NoREC 还直接指出了传统 differential testing 的一个痛点，即不同 DBMS 的 SQL dialect 和语义细节差异会显著限制 cross-DBMS comparison 的可用范围。这一点恰好从反面说明了本项目为什么必须引入 unified DSL、semantic normalization 和 capability-aware target registry：如果没有这几层中间抽象，跨 pandas、Polars、DuckDB、PyArrow、DataFusion 等系统的差分比较会迅速被非 bug 语义差异淹没。不过，NoREC 主要针对 SQL optimizer 和 WHERE clause 重写相关错误，输入和 oracle 都高度依赖 SQL 结构；本项目则需要进一步覆盖非 SQL 操作、API lowering、Arrow slice/chunk/layout 差异，以及多种执行模式下的同义工作流。

TLP 或更一般的 Query Partitioning，测试目标是 SQL 查询处理中 WHERE、GROUP BY、HAVING、aggregate、DISTINCT 等场景下的逻辑错误。它的测试目的，是把一个原始查询依据 TRUE/FALSE/NULL 三值逻辑拆分成多个 partitioning queries，再检查这些分区查询组合后的结果是否与原查询一致。TLP 与本项目的联系非常紧密，因为它体现了一个与你的 metamorphic/differential oracle 高度一致的思想：并不需要一个外部“正确答案”，只要能构造多个理论上必须等价的执行形态，就能自动判错。TLP 也说明，真正有效的 oracle 往往来自对被测语言语义本身的深入理解，而不是纯粹的语法随机化。与本项目的关键差异在于，TLP 的等价关系建立在 SQL 三值逻辑和 SQL 查询分解之上，而本项目的等价关系需要覆盖更宽的 API 族与执行模型，例如 DataFrame filter、sort、top-k、coalesce、semi/anti join、nullable bool reduction、Arrow slice rebuild equivalence 等。这意味着本项目的 metamorphic relation 集合不会像 TLP 那样集中在单一逻辑体系中，而必须拆散在多类 common workflow semantics 里。

DQE 把 SQL wrong-result testing 从 SELECT 扩展到了 UPDATE 和 DELETE。它的测试目标，是检测同一谓词在 SELECT、UPDATE、DELETE 三类语句中访问行集合不一致的问题。它的测试目的，是利用“同一 predicate 应访问同一批记录”这一跨语句一致性原则，检测 DBMS 内部 predicate evaluation 不一致造成的错误结果和错误状态修改。DQE 与本项目的相似性在于，两者都非常强调 differential consistency，而不是只比较最终查询结果值；两者都利用“相同语义意图在多个执行路径下应保持一致”这一更抽象的原则构造 oracle。DQE 的重要价值还在于，它清楚展示了 logic bug testing 不一定局限于 SELECT wrong-result，也可以扩展到状态变更类语句。与本项目的差异则在于，DQE 的一致性比较仍然发生在同一个 SQL DBMS 内部不同语句类型之间，而本项目的一致性比较通常发生在不同 family、不同 API 和不同 execution adapter 之间。因此，DQE 提供的是“intra-system semantic consistency oracle”的范式，而本项目更像“inter-system semantic consistency oracle”的扩展版本。

### Guided Testing、Coverage Feedback 与 Metamorphic Testing

在 guided testing 方向，SQLRight、QPG 和 SQUIRREL 是最值得比较的三篇。SQLRight 的测试目标是 DBMS logical bugs；测试目的是把 coverage-based guidance、validity-oriented mutation 和已有 DBMS oracles 结合起来，以比无引导的 grammar-based generation 更有效的方式探索深层程序状态。SQLRight 和本项目的共同点在于，都明确反对只靠无引导随机生成；都认为 validity 或 semantic correctness 是进入深层执行逻辑的必要前提；都把自动 oracle 与 bug evidence discovery 放在核心位置。关键差异在于，SQLRight 的 guidance signal 主要还是代码覆盖及其派生状态，输入也仍以 SQL query mutation 为主。而本项目即使借鉴 guidance 思路，其重点也不会放在单个 DBMS 的内部 coverage 最大化上，而是放在跨目标族的 semantic risk、family saturation、lane scheduling、candidate reward 和 fresh-vs-known separation 上。换句话说，SQLRight 解决的是“如何更高效地驱动 SQL logic-bug oracle”，而本项目还要解决“如何把多个不同生态后端组织进同一 latest-version discovery-runing workflow”。

QPG 的测试目标是 relational DBMS 中需要更复杂 query plan 才能暴露的 logic bugs；测试目的是利用 query plan 作为 guidance signal，优先生成能触发新 physical plan 的数据库状态和查询组合。QPG 与本项目共享一个重要立场：在 stateful 数据系统中，传统代码覆盖并不是唯一甚至最好的指导信号，更贴近执行语义的结构性反馈可能更有效。QPG 将这个思想具体化为 query plan diversity，而本项目则更倾向于使用 operation semantics、pattern risk、cross-family workflow lane、metamorphic relation 命中情况以及 candidate family novelty 等更高层的语义反馈。两者最大的差异仍然是系统边界。QPG 只需依赖单个 DBMS 暴露出的 EXPLAIN 计划，因此可以把 query plan 作为黑盒引导信号；本项目则没有一个可在 pandas、Polars、PyArrow、DuckDB、SQLite、DataFusion 上统一读取且统一解释的“query plan”概念。因此，你的 guidance 更接近语义模式驱动与目标族驱动，而不是统一 plan-space 驱动。

SQUIRREL 的测试目标则主要是 DBMS 的 memory-error/security bugs；测试目的是通过 structured IR、syntax-preserving mutation 和 semantics-guided instantiation，在保证 SQL 输入高语言有效率的同时深入 DBMS 内部并发现可导致 CVE 的安全错误。SQUIRREL 与本项目的相似点在于，两者都认同“有效输入比随机比特翻转更重要”，都使用某种结构化中间表示，都认为生成过程必须理解语义依赖才能有效触达深层执行路径。但 SQUIRREL 的核心结果是 memory-safety 和 security bugs，而本项目的核心结果是 semantic wrong-result bugs。前者的价值主要体现在安全影响和 deeper code coverage 上，后者的价值则主要体现在 silent data corruption、wrong analysis result 和 reproducible latest-version correctness bug family 上。因此，SQUIRREL 可以作为“为什么结构化、语义感知的输入生成是必要的”这一点的支撑文献，但不能替代本项目对 semantic differential testing 的定位。

在 metamorphic testing 方向，Metamorphic Testing of Datalog Engines 是一个非常有价值的邻近工作。它的测试目标是 Datalog engines 的 wrong-result bugs；测试目的是利用 metamorphic relations 在没有显式 ground truth 的情况下检测等价执行是否保持结果一致。它与本项目最像的地方，不在于具体被测语言，而在于它把 metamorphic relation 当作核心 oracle，而不是把变形测试视为附属技巧。这一点与你项目中的 metamorphic lane、idempotence/rewrite equivalence、slice rebuild equivalence、limit/top-k pagination equivalence 等设计高度一致。关键差异在于，Datalog engine 的语义域比 DataFrame/Arrow/SQL 混合生态窄得多，不需要面对 dtype coercion、nullable bool、Arrow memory layout、eager/lazy execution 以及 API lowering 这些异构语义边界。因此，本项目可以借鉴这类工作的论证方式来说明 metamorphic oracle 的必要性，但仍必须强调自己面对的是更异构、更工程化的真实数据处理生态。

## 可直接引用的定位总结

如果需要用一段更短的话来概括上述对比，可以写成下面这样：

> 现有工作要么关注 DataFrame workflow generation 与 replay，要么关注单一 SQL DBMS 的 wrong-result bug oracle，要么关注 coverage- 或 plan-guided 的测试生成效率。相比之下，本项目的重点不在于提出一种新的单点 oracle 或新的单后端 fuzzer，而在于将统一 DSL、semantic normalization、differential/metamorphic/deterministic oracles、candidate triage、issue bundle 和 latest-version confirmation tracking 组合成一套跨 DataFrame、Arrow、embedded SQL 和 query engine 的统一 discovery-runing framework。该框架既吸收了 FuzzyData 在 workflow abstraction 方面的思想，也借鉴了 PQS、NoREC、TLP、DQE 等 DBMS oracle 设计经验，以及 SQLRight、QPG 等 guided testing 的方法元素，但其目标是更广的跨生态语义一致性与可上游提交的 latest-version bug evidence，而非单一系统中的局部测试优化。
