# Automated Bug Detection Workflow

This project separates exploratory fuzzing from deterministic latest-version
bug audit.

## Directory Layout

- `src/datadiff/bug_audit.py`: deterministic probes and verdict logic.
- `src/datadiff/bug_status.py`: lightweight status aggregation over issue/evidence files.
- `src/datadiff/issue_bundle.py`: issue reproducer extraction and portable evidence bundle generation.
- `src/datadiff/issue_readiness.py`: local issue draft submission-readiness audit.
- `reports/bug-audit-*.json`: local run evidence; ignored by git like other run reports.
- `reports/bug-audit-*.md`: local human-readable audit report.
- `reports/bug-status-*.json` / `.md`: optional current-state snapshot from `datadiff bug-status --write-report`.
- `reports/issue-readiness-*.json` / `.md`: optional local issue submission queue audit.
- `new_issue/generated/manifest.json`: uploadable evidence manifest generated from the same audit run.
- `new_issue/generated/bug-hunt-manifest.json`: integrated hunt manifest linking audit, fuzz run, report, and classification.
- `new_issue/generated/bug-hunt-manifest-fresh-candidates.json`: uploadable full case/output evidence for fresh fuzz candidates.
- `new_issue/generated/README.md`: notes for generated evidence files.
- `new_issue/generated/*.md`: raw issue drafts generated by project code.
- `new_issue/generated/issue-bundles/`: extracted reproducers and bundle manifest for reportable issues.
- `new_issue/*.md`: reviewed issue drafts and submitted/new issue records.
- `old_issue/*.md`: issues that were already reported by others and are kept for deduplication.

`study/` is intentionally ignored and not part of the project artifact.

## Command

```bash
.venv/bin/datadiff bug-audit
.venv/bin/datadiff bug-audit --write-issues --overwrite-issues
.venv/bin/datadiff bug-hunt --cases 500 --seed 1
.venv/bin/datadiff bug-sprint --list-lanes --json
.venv/bin/datadiff bug-sprint --cases 100 --seeds 1
.venv/bin/datadiff bug-sprint --cases 100 --seeds 1 --watch-health
.venv/bin/datadiff bug-sprint-status --manifest new_issue/generated/bug-sprint-manifest.json
.venv/bin/datadiff candidate-pipeline --manifest new_issue/generated/bug-sprint-manifest.json
.venv/bin/datadiff run-health
.venv/bin/datadiff run-health --fail-on-fresh-candidate --fail-on-bug
.venv/bin/python scripts/run_final_experiments.py --track validation --validation-cases 200 --jobs 1
.venv/bin/datadiff bug-hunt --cases 2000 --seed 1 --preset live_deep_organic_metamorphic
.venv/bin/datadiff bug-status
.venv/bin/datadiff bug-status --json --write-report
.venv/bin/datadiff issue-readiness
.venv/bin/datadiff issue-readiness --json --write-report
.venv/bin/datadiff issue-bundle
.venv/bin/datadiff issue-bundle --run-reproducers
.venv/bin/datadiff methodology-report --manifest runs/experiment-YYYYMMDDTHHMMSS.json --refresh
.venv/bin/datadiff review-readiness --json --write-report
```

The validation track emits `--evidence-mode validation`; it gates harness health
before long runs and is not counted as live bug evidence.

The command runs fixed probes against the installed library versions. A probe is
counted as a candidate implementation bug only when its encoded invariant is
violated. Some probes also run a deterministic sweep of related variants, so the
manifest records whether the problem is an isolated example or a larger family.
The generated manifest records:

- runtime environment and dependency versions;
- probe id and target backend;
- invariant under test;
- expected value;
- observed value;
- sweep details, when a probe has variant generation;
- automatic verdict;
- candidate family key.

`bug-hunt` is the end-to-end project entry point. It runs:

1. deterministic `bug-audit`;
2. latest-version guided fuzzing with the selected live preset;
3. markdown/csv report generation;
4. automatic classification of fuzz findings;
5. a portable manifest in `new_issue/generated/bug-hunt-manifest.json`.
6. a portable candidate evidence JSON containing the full generated case,
   normalized backend outputs, and automatic finding verdict for each fresh
   family row.

The classification output separates `fresh_candidate_bug_families`,
`issue_inspired_unsaturated_candidate_bug_families`, and
`known_saturated_candidate_bug_families`. `fresh_candidate_bug_families` is now
reserved for non-saturated organic findings. Issue-inspired cases remain useful
for regression pressure and root-cause expansion, but they are not automatically
counted as newly discovered bugs without manual upstream deduplication.
This keeps repeated old roots as evidence while preventing them from being
counted as new latest-version bugs.
The main manifest also embeds the deterministic audit results, so the uploaded
artifact does not depend on ignored local `reports/` or `runs/` files to show
which invariant produced a verdict.

`bug-sprint` runs several narrow lanes instead of one broad all-engine run. The
default lane set covers Arrow layout, Polars lazy execution, Polars streaming,
DataFusion optimizer/metamorphic SQL, DataFusion common API workflows, embedded SQL, and cross-family latest
testing without DataFusion. It also includes `common_api_workflow`, a low-cost
organic lane for everyday DataFrame/Arrow/SQL operations such as filter, drop-null/dropna, mutate,
string contains/starts-with/ends-with/strip/replace/slice/concat, nullable boolean not, numeric abs/clip, union-all/concat, semi/anti join, fill-null/coalesce, multi-column coalesce, case-when, distinct, nullable distinct top-k, join, groupby, sort, limit/offset, and projection. The deep default lanes use
`bughunt_fresh`, and `common_api_workflow` uses an organic daily-workflow
generator, so they do not actively inject cases from known upstream issues.
Optional stress lanes such
as `arrow_probe_stress`, `polars_probe_stress`, and `duckdb_probe_stress` can be
selected explicitly; issue-inspired results from those lanes remain separated by
classification and are not counted as organic fresh bugs. Each lane has its own
target suite and live preset, but all lanes share the same runner, oracle,
classification, generated evidence, and saturated-family policy. The output
manifest is `new_issue/generated/bug-sprint-manifest.json`, with per-lane
`*-fresh-candidates.json` files when fresh candidates appear. `--list-lanes
--json` exposes the lane catalog for experiment scripts.

`bug-sprint` now reorders remaining lanes with adaptive weights from recent lane
yield, novelty, and false-positive penalty, and records the score/budget
summary in the manifest for the next budgeting round.
`bug-sprint --watch-health` records each completed run's health summary in the
manifest and stops remaining lanes after a bug row or organic fresh candidate.
`run-health` is the low-cost monitor for in-progress and completed run logs.
It reads the newest run by modification time when `--run-file` is omitted, can
tolerate a gzip log that is still being written, and reports row counts,
statuses, candidate families, known-saturated families, false-positive reasons,
and a few examples. Use `--fail-on-fresh-candidate --fail-on-bug` in a watchdog
loop to stop a long sprint as soon as a candidate appears, so CPU time is spent
on triage instead of repeatedly exploring the same newly discovered hotspot.
`bug-sprint-status` sits one layer above `run-health`: it reads the sprint
manifest, reports current lane/seed progress, attaches the latest observed
run-health summary for the active guided sprint, and prints the recent lane
yield scoreboard that drives the next-lane budget decision.

When a fresh candidate appears, `bug-hunt` and `bug-sprint` automatically run a
candidate pipeline: freeze -> recheck -> reduce -> dedup -> issue-readiness.
The resulting manifests live under `new_issue/generated/candidate-pipelines/`.
`candidate-pipeline --manifest ...` can replay the same post-processing flow for
existing `bug-hunt` or `bug-sprint` manifests.

`classify-run --json` is the offline oracle/triage entry point. It reads saved
run logs, can optionally use `--refresh` to recompute findings from stored
normalized outputs with the current oracle, and emits `offline_buckets`:
`new_bug`, `known_bug`, `false_positive`, `semantic_divergence`, plus residual
`needs_triage`/`unclassified`. This is the stable paper-table policy: new bugs
must be non-replay, non-source-issue, non-known-saturated candidates; known bugs
cover replay/source-issue/known-saturated candidates; semantic divergences and
false positives never enter bug counts.

`bug-status` is intentionally lightweight. It reads the latest confirmation
registry, `new_issue/`, `old_issue/`, and generated manifests, but it does not
scan large run logs. Its summary separates current unsaturated fresh candidates
from recorded historical fresh signals that have since become known/saturated.
This makes the project state machine-readable without relying on AI/manual
counting.

`issue-readiness` is the pre-submission queue audit. It reads the same local
lightweight evidence, plus the issue draft bodies in `new_issue/`, and assigns
each draft to one conservative state: ready to submit, needs a final duplicate
check, needs more reproducer/evidence, already submitted/confirmed, or not
reproducible on the current latest version. It never upgrades a candidate to a
confirmed bug; only the latest confirmation registry can make a draft eligible
for paper confirmed-count reporting.

`issue-bundle` turns the readiness queue into portable submission artifacts. By
default it bundles `ready_to_submit` and `needs_dedup_check` drafts, extracts
their Python reproducer blocks into `new_issue/generated/issue-bundles/`, and
writes a manifest that records issue path, family, readiness status, extracted
script path, syntax-check result, and optional execution stdout/stderr. Running
the reproducer is evidence capture, not confirmation; upstream labels, fixes, or
maintainer responses still control the confirmed bug count.

`review-readiness` is the paper-facing audit. It checks documentation, target
registry breadth, layered implementation modules, automated bug evidence,
issue-bundle reproducers, fresh/replay/known separation, reproducibility
commands, the final validation/live/historical/seeded/ablation/comparison
experiment protocol, artifact hygiene, methodology tests, and the confirmed
latest bug-family target. The default confirmed-family target is 20; failing
that gate is reported explicitly so candidate issues are not confused with
upstream-confirmed bugs.

## Deep Organic Presets

`bug-hunt` defaults to `live_deep_organic`. This preset uses the `bughunt_fresh`
generator profile, so it does not actively inject cases derived from known
upstream issues. Its guidance targets cover DataFrame API behavior, Arrow table
layout, embedded SQL execution, query engine execution, nullable/extension
dtypes, slicing/chunking, sortedness, window/running aggregates, and numeric
edge cases.

`live_deep_organic_metamorphic` uses the same organic target set and adds the
metamorphic oracle. It is the preferred longer-run setting when the goal is to
find new root causes rather than replay known saturated families.

`live_issue_focus` and backend-specific `*_issue_focus` presets remain useful
for regression pressure and root-cause expansion, but their findings are kept
separate from organic fresh counts by classification.

## Current Deterministic Probes

| Probe | Target | Invariant |
| --- | --- | --- |
| `datafusion_limit_idempotence` | DataFusion | Repeating the same ordered `LIMIT` over the same subquery must not change query results. |
| `polars_reflected_arithmetic` | Polars | `Series.__r*__(other)` must evaluate `other op self` for reflected arithmetic. |
| `polars_vector_division_rounding` | Polars | Vectorized division must match the same IEEE-754 result as the single-row/Python path; the probe sweeps integer numerator/denominator pairs. |
| `polars_slice_chunk_lazy_equivalence` | Polars | Equivalent sliced, multi-chunk, rebuilt, and lazy tables must agree for group/filter/sort operations. |
| `pyarrow_sliced_bool_groupby` | PyArrow | A sliced table must group/aggregate like an equivalent zero-offset rebuilt table; the probe sweeps offsets, group layouts, Boolean values, and `any`/`all`. |
| `pyarrow_sliced_transform_equivalence` | PyArrow | A sliced table must filter, sort, and take like its zero-offset rebuilt equivalent across nullable Boolean layouts. |

The equivalence probes remain in the audit even when their current verdict is
clean. They turn newly covered execution paths into repeatable regression
searches on later library versions instead of leaving them as one-off manual
experiments.

## Fresh Hunt Policy

Fresh fuzzing should keep known saturated families enabled in the config instead
of replacing them with a partial command-line list. Otherwise old duplicated
families can reappear as candidate findings. For example,
`csv_long_numeric_roundtrip@duckdb` and `csv_long_numeric_roundtrip@pyarrow`
are known/saturated and should not be counted as newly discovered bugs.
All source issues declared by issue-inspired generator profiles are also covered
by the default replay source gate, and a contract test enforces that coverage.
Families emitted by `bug-audit` are also added to the default saturated list
after they become part of the generated evidence, so later fresh hunts focus on
new root causes instead of rediscovering the same issue.

## Reporting Rule

For paper or project reporting, use bug family count, not raw finding count.
Repeated probes or multiple symptoms under the same root family are grouped by
`family@backend`. Current automatically detected families are stored in
`new_issue/generated/manifest.json`.
